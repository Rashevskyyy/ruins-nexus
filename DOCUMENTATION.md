# Cosmic Frontier — документация по текущему состоянию репозитория

> Документ описывает **то, что уже реализовано** в коде и как этим пользоваться.
> Для полного списка правил и параметров игры см. `CURRENT_STATE.md`.

## 1) Назначение репозитория

**Cosmic Frontier** — сетевой браузерный прототип кооперативно‑соревновательной настольной стратегии.
Проект состоит из клиентского приложения на PixiJS (рендер + UI) и серверного компонента на Socket.IO,
который хранит состояние игры и применяет правила (server‑authoritative).

## 2) Технологический стек

- **Клиент:** TypeScript + PixiJS + Vite.
- **Сервер:** Node.js + Express + Socket.IO.
- **Схемы:** Zod для валидации игровых действий на сервере.
- **Инфраструктура:** подготовлены конфиги для Vercel/Railway.

## 3) Скрипты и локальный запуск

Сценарии запуска определены в `package.json`:

```bash
npm install
npm run dev        # клиент (Vite)
npm run server     # сервер (tsx)
npm run dev:all    # клиент + сервер
npm run build      # сборка клиента
npm run preview    # предпросмотр сборки
```

При разработке сервер стартует отдельным процессом (см. `server/index.ts`).

### 4.1) Клиент (`src/`)

- `main.ts` — точка входа: инициализация Pixi, загрузка ассетов, лобби, подключение к серверу, синхронизация состояния.
- `core/` — ядро правил (Game/GameState/Phase/модификаторы).
- `board/` — логика карты и генерация колоды тайлов.
- `entities/` — сущности (игрок, расы, предметы, юниты, типы построек).
- `systems/` — подсистемы: бой, исследование, торговля, крафт.
- `render/` — визуализация PixiJS.
- `screens/` — UI экраны (лобби, загрузка и т.д.).
- `network/` — клиент Socket.IO.

### 4.2) Сервер (`server/`)

- `index.ts` — сервер Socket.IO с валидацией действий через Zod и хранением состояния матча на сервере.

## 5) Сетевая архитектура (server‑authoritative)

Сервер реализует **server‑authoritative** модель:
- Клиент отправляет **намерение** (action + параметры).
- Сервер **валидирует** действие и применяет правила.
- Сервер **отправляет** новое состояние всем клиентам.

Это защищает от рассинхронизации: клиенты не присылают полное состояние,
сервер является источником истины.

### 5.1) Типы действий

Сервер принимает набор игровых действий (см. `server/index.ts`), среди которых:
- базовые (`explore`, `move` через `hex-click`, `gather`, `trade`, `heal`),
- строительство (`build-base`, `build-modules`),
- крафт (`craft`),
- финальные действия (`final-trial`),
- сервисные (`reset-game`, debug‑инструменты).

## 6) Клиентский жизненный цикл

1. **Инициализация PixiJS** и загрузка ассетов.
2. **Показ лобби** и подключение к Socket.IO.
3. **Старт игры**: получение initial state от сервера.
4. **Синхронизация**: клиент применяет серверное состояние и обновляет рендер.
5. **Reconnect**: при перезагрузке страницы пытается восстановить сессию.

## 10) Что важно помнить при расширении

- Сервер **обязан** оставаться источником истины: любые правила и RNG должны быть на сервере.
- Клиент должен обновляться только на основе **серверного состояния**.
- Для новых фич обязательно расширять действия в Zod‑схеме и добавлять обработчики на сервере.
